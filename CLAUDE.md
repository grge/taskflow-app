This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # dev server at http://localhost:5173
npm run build    # production build → dist/
npm run preview  # preview production build
npm test         # core/replica/export unit tests under five timezones, then test:server
npm run test:server  # reference backend: conformance suite, persistence, real sync clients through it
npm run test:e2e # build, then the Playwright smoke and sync suites against vite preview
npm run server   # run the backend locally (DATA_DIR, TZ, ALLOWED_ORIGINS); `npm run server -- token create --name dev`
```

No lint is configured. `test:e2e` uses the installed Playwright Chromium; set `PW_CHROMIUM` to point it at a specific browser binary. The smoke suite pins the clock and timezone and asserts on what lands in localStorage, so it is the characterization net for refactors. The sync suite (`tests/e2e/sync.mjs`) runs browsers against the reference backend in-process on a real clock (a backend applies ops stamped far in the future at its own time).

## Architecture

TaskFlow is a Svelte 5 SPA (no SvelteKit) that schedules tasks by minimizing accumulated "pressure" — a time-dependent urgency function per task that rises from an `onset` date toward a `peak` date/value. State lives in localStorage (`taskflow_v2`). A device can optionally connect to a self-hosted sync backend (`server/`, see `SYNC-AND-API-DESIGN.md`) from Settings → Sync backend; the reference one is deployed as `taskflow-sync` on fly.io.

### Layer overview

- **`src/core/`** — the domain core: `apply(state, op, { now }) → { state, result }` (`apply.js`) is the only place app data changes. An op is `{ id, type, args, at, tz, actor }`; `OP_TYPES` is the catalogue (`task.*`, `schedule.*`, `timer.*`, `hours.update`, `block.*`). It is pure: it never reads the clock (time comes from `context.now`, the op's `at`), never mutates its input, and returns untouched slices by identity. Times are host-local by contract. It is also deterministic: no randomness, so scheduler-made blocks get ids derived from task, day and start (`blockId` in `scheduling.js`); anything that needs a fresh id takes it in the op's args. `state.js` is the stored/exported shape (`reviveState`, `serializeState`, `checkStateData`). `live.js` folds an unflushed timer into elapsed time. The same core will run on a device and on a backend (`SYNC-AND-API-DESIGN.md`).
- **`src/sync/`** — `replica.js`: the device's copy as the sync protocol sees it, `{ base, version, pending }`, pure functions (`applyLocal`, `commitLocal`, `receive`, `rebase`, `forget`). Current state is base with pending replayed; `receive` checks each batch's `hash` (`stateHash` in `core/state.js`) and reports `diverged` when this device can't reproduce the backend's state (different core or timezone), so the backend always wins. Local-only mode commits after every op, so pending is empty between ops. `client.js`: replica + fetch + WebSocket against one backend (send queue, stream, catch-up, reload, reconnect); runs in browser and Node. `connect.js`: connect links (`#connect=` base64url `{ url, token }`), URL checks, `probeBackend` (protocol and token checked before anything is saved), `firstConnectPlan` (download / upload / ask) and `mergeStates` (union by task id, newer `lastModifiedAt` wins, backend's work hours).
- **`server/`** — the reference backend: `cli.js` (serve, `token create|list|revoke`, `export`), `app.js` (node:http + `ws`: `/v1/info`, `/v1/state`, `/v1/ops`, `/v1/stream`, CORS, rate limit; applies ops synchronously, one writer), `store.js` (node:sqlite: current state written with each op, op log, hashed tokens). `Dockerfile` and `fly.toml` at the repo root; deploy steps in `server/README.md`. `scripts/core-version.mjs` hashes `apply.js` and its imports into `coreVersion`, injected into the app by `vite.config.js`. `tests/conformance/` is the protocol suite, runnable against any backend.
- **`src/lib/`** — pure logic: `envelope.js` (pressure math: `pAt`, `accumulatedPressure`, `getPressureTier`, `pToColor`), `scheduler.js` (auto-scheduler: greedy + local search), `outlook-scheduler.js` (reorder/bump-forward packing for the Outlook backlog), `scheduling.js` (block placement, multi-day splitting), `calendar.js` (work-day navigation, date formatting), `dnd.js` (drag-and-drop Svelte actions), `persistence.js` (localStorage load/save/migration), `tasks.js` (task factory), `constants.js` (storage key, pressure scale/color stops, default work schedule)
- **`src/stores/`** — Svelte 5 rune-based state. `data.svelte.js` holds the four persisted slices (`tasks`, `workSchedule`, `fixedBlocks`, `activeTimer`) as `$state.raw` and exposes `dispatch(type, args)`, which stamps an op (args JSON-normalised, so what is applied is what would be stored or sent) and runs it through the replica, plus `exportData`/`readImport`/`importData` for Settings' "Your data" section. While a backend is connected, ops go through a sync client instead of `commitLocal`; `connect(probe, { token, choice })` makes the backend's state the base and queues any upload or merge as one `data.import`, `disconnect()` commits whatever is pending locally, and `sync` exposes status, pending count and notices (header pill and notice bar in `App.svelte`, labels from `lib/sync-status.js`); `tasks.svelte.js` and `schedule.svelte.js` are thin wrappers over `dispatch` with the long-standing function names. Others: `ui.svelte.js` (active tab/modal; `activeTimer` re-exports the data store), `clock.svelte.js` (ticking now/today), `estimation.svelte.js` (learned duration multiplier), `theme.svelte.js` (selected color theme), `layout.svelte.js` (manually resized task-panel width)
- **`src/lib/components/`** — UI: `App.svelte` is the root shell with Plan/Insights/Settings tabs; `TodayPlanner.svelte` is today's vertical timeline; `OutlookSection.svelte` is the future-day backlog with drag-to-reorder; `TaskList.svelte`/`TaskRow.svelte` is the task panel; `EnvelopeEditor.svelte` is the drag-to-edit onset/peak chart; `AddTaskModal.svelte`/`AddBlockModal.svelte`/`SettingsModal.svelte`/`InsightsModal.svelte`; `TimerBar.svelte` for active time tracking; `MobileNav.svelte` is the phone bottom nav; `PanelResizer.svelte` is the task-panel drag handle

### Key conventions

**Svelte 5 state exports:** Svelte 5 forbids exporting reassignable `$state` from `.svelte.js` modules. All stores export objects with `get value()` accessors. The persistence `$effect` must run inside a component (done via `initPersistence()` called in `App.svelte`).

**Drag-and-drop:** One pointer-event engine (`pointerDrag` in `dnd.js`) drives all four surfaces; there is no drag library. Hit-testing is `document.elementsFromPoint()` via `dnd-hittest.js` (reliable for overlapping/scrolling); placement math lives in `drop-placement.js`; preview blocks render in `previewBlock` (UI store) without touching `scheduledBlocks`. The pointer is captured on `pointerdown`, not on first move — the cards are small enough that a drag leaves them immediately, and without capture the move that starts the drag goes to whatever is underneath. On touch a press must dwell (`liftGate`, 200ms) before it becomes a drag, so a swipe still scrolls the list; the lifted card gets `.is-lifted`. Dragging near a panel edge autoscrolls it (`edgeScroller`).

**Multi-day block splitting:** Tasks can span multiple days; blocks carry `partIndex`/`totalParts`. Grab-offset logic differs: single blocks use pixel offset (`grabOffsetPx`), split blocks use time offset (`grabOffsetMinutes`) with `retreatWork()`.

**Auto-scheduler:** Greedy packing first, then binary-search local optimization. `estimationMultiplier` (median of elapsed/estimated ratios from completed tasks, prior 1.2× until 5 observations) is computed in `estimation.svelte.js` but is only displayed in Insights; it is not applied to durations when packing. The Outlook backlog uses a separate, simpler sequential-packing scheduler (`outlook-scheduler.js`) for reorder/bump-forward, spilling overflow to subsequent work days.

**Timer:** Single `activeTimer` state: `{ taskId, startedAt, baseSeconds }`. `startedAt` is `null` when paused. Display = `baseSeconds + (now - startedAt)`. Written to `task.elapsedSeconds` on pause/stop.

**Pressure model:** Each task has `onset`, `peak` (Dates) and `peakPressure` (0–1). `pAt()` rises linearly from 0 at onset to `peakPressure` at peak, then holds flat (deliberately piecewise linear; the editor's drawn curve is smoothed on purpose and is not the model). Five tiers (Low/Building/Elevated/High/Critical) and a matching 6-stop color gradient (green → dark red) are defined in `constants.js` (`PRESSURE_SCALE`, `ENVELOPE_COLOR_STOPS`). `EnvelopeEditor.svelte` lets onset/peak/peakPressure be dragged directly on a 7-day chart — there are no presets.

**Task list order:** Insertion order is preserved (sorted-by-pressure was reverted — it was disorienting in practice).

**Lock (`isLocked`):** A per-task padlock (`toggleLock` in `tasks.svelte.js`) protecting a task from bulk/automatic scheduling ops only. Locked + unscheduled → excluded from `autoSchedule`'s candidate pool (parked/blocked). Locked + scheduled → skipped by `clearSchedule` (kept while the rest clears, so you can reschedule around it — locked-scheduled tasks already flow into `manualBlocks`, so packing around them is automatic). The lock never blocks manual drag/delete/edit/complete. The toggle lives on the card in every state: the draggable chip in `TaskRow`, the timeline block in `TodayPlanner`, and the backlog card in `OutlookSection` — each hover-reveals when unlocked, stays visible when locked, and stops `mousedown` propagation so the drag action doesn't swallow the click. No persistence migration: old tasks lack the field and read falsy (unlocked).

**Panel sizing:** The task panel is fluid (`clamp(300px, 34vw, 380px)`) until dragged, after which `layout.svelte.js` holds an explicit width in `taskflow_layout` and `App.svelte` applies it as `--task-panel-w`. `null` means never resized, so the default stays fluid rather than freezing at a number; double-click or Home on the handle returns to it. Clamped to 240–560px and to leaving the work region 360px, with `max-width: 60vw` as the backstop for a width saved on a wider window. The handle is hidden in the stacked phone layout, where the panel is full width.

**Theming:** `theme.svelte.js` stores the selected theme name (`warm-parchment` default, plus `sage-morning`, `ember-night`, `dusk`) in localStorage under `taskflow_theme` and sets `data-theme` on `<html>`; `themes.css` defines the CSS variables per theme. Selected from `SettingsModal.svelte`.

**Persistence:** `taskflow_v2` holds the current state (unchanged shape, also the export file's shape, and byte-identical through export → import → export). `taskflow_sync` holds `{ version, pending, base }` only while something is pending or a backend version is known; on load, pending ops replay on `base` (and stay pending if connected). `taskflow_backend` holds `{ url, token }` while connected. A `#connect=` link is read once in `App.svelte`, removed from the address bar, and only fills in Settings' form; nothing connects without a click. Load revives date fields and fills defaults for older saves. Soft deletes (`isDeleted: true`). Completing a task clears its `scheduledBlocks`. Disabling a work day unschedules blocks on that day.
